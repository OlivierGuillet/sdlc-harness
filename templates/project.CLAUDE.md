# Project rules (SDLC harness)

This project uses the SDLC harness: specs are written with cc-sdd, everything
after the specs is done with superpowers. Start Claude Code from this directory
(the one that contains `.harness`), otherwise the project skills and the
guardrail hooks are not loaded.

## Paths

- Steering: `docs/steering/`
- Specs: `docs/specs/<feature>/`
- Architecture Decision Records: `docs/adr/`

## Language

- Reply to the user in the language they write in.
- Code, identifiers, file names, commit messages, specs, ADRs and documentation
  are written in English.

## Workflow

| Phase | Tool |
|---|---|
| Steering (optional) | cc-sdd: `/kiro-steering`, `/kiro-steering-custom` |
| Discovery | cc-sdd: `/kiro-discovery "idea"` |
| Requirements (EARS) | cc-sdd: `/kiro-spec-init`, `/kiro-spec-requirements {feature}`, plus the `harness-sdlc:ears-spec` skill |
| Design, task breakdown | cc-sdd: `/kiro-spec-design {feature}`, `/kiro-spec-tasks {feature}`, `/kiro-validate-*` |
| Progress | cc-sdd: `/kiro-spec-status {feature}` |
| Architecture decisions | `harness-sdlc:adr` skill, in `docs/adr/` |
| Designing anything new | superpowers `brainstorming` |
| Planning the implementation | superpowers `writing-plans`, fed by `docs/specs/<feature>/tasks.md` |
| Implementation | superpowers `test-driven-development`, with `subagent-driven-development` or `executing-plans` |
| Bugs and failing tests | superpowers `systematic-debugging` |
| Review | superpowers `requesting-code-review`, `receiving-code-review` |
| Completion | superpowers `verification-before-completion`, then `finishing-a-development-branch` |

At the start of every task, invoke `superpowers:using-superpowers` and follow
the skills it points to.

## Rules

- Never use `/kiro-impl` or `/kiro-spec-batch`: implementation belongs to superpowers.
- Do not use `kiro-review`, `kiro-debug` or `kiro-verify-completion`. cc-sdd
  installs them, but review, debugging and verification go through the
  superpowers skills listed above.
- Requirements, design and tasks are approved by a human one phase at a time.
  Use `-y`, or `/kiro-spec-quick --auto`, only when the user asks for a fast track.
- When a task from `docs/specs/<feature>/tasks.md` is done and verified, tick
  its checkbox in that file. `/kiro-impl` used to do it, and
  `/kiro-spec-status` reads those checkboxes.
- Each acceptance criterion has the ID `REQ-<feature>-<N>.<M>` (requirement N,
  criterion M). Every ID gets at least one test that carries it in its name,
  written before the code.
- A change to a dependency, a build manifest or the architecture needs an ADR.
- After `/kiro-discovery` and after each `/kiro-spec-design`, write one ADR per choice made between real alternatives
  (framework or library adopted or rejected, persistence, networking,
  concurrency model, module boundaries, minimum OS), with the
  `harness-sdlc:adr` skill. cc-sdd records these choices in `roadmap.md`,
  `brief.md` and `design.md` but never writes ADRs. Do it before ending the
  turn, with status `Proposed` until the user accepts, and link each ADR to the
  document that made the choice.
- When a harness hook blocks, fix the cause (write the spec, the ADR, the EARS
  sentence). Never work around a hook.

## Steering

For spec and implementation work, load `product.md`, `tech.md` and
`structure.md` from `docs/steering/` when they exist. Load other steering files
only when they are relevant to the task.

## Maintenance

This file is installed by the harness (`templates/install-claude-md.sh` in the
sdlc-harness clone). Running `npx cc-sdd` again may overwrite it; run the
install script again afterwards. Keep the first line: the harness uses it to
recognise the file. Do not edit this file by hand: the install script replaces
it (after a backup) whenever it differs from the template. Put project-specific
rules in `docs/steering/` or change the template in the harness.
